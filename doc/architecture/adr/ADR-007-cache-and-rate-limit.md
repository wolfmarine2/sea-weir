## Context(上下文)

### 问题陈述

中继面每请求需要认证令牌、读用户信息、选渠道、限流判定,全部直查 DB 不可行;多节点部署又要求缓存一致。原实现以「Redis 可选 + 60s TTL + 60s 轮询同步」获得简单性,但变更生效滞后最长 60s。需要设计两级缓存与限流方案,并明确降级行为。

### 约束条件

- 公司标准缓存为 Valkey(Redis 协议)
- 多节点:渠道/配置/令牌变更需快速生效(目标 ≤1s)
- Valkey 不可用时系统需可运行(降级),但吊销等安全语义不能失效

### 驱动力

- 性能:认证/选路热路径亚毫秒
- 一致性:变更快速生效(pub/sub 失效广播)
- 韧性:明确的降级矩阵

### 目标状态

热路径零 DB;变更 ≤1s 全节点生效;Valkey 故障时按降级矩阵运行。

### 备选方案

#### 方案 A:Valkey 读穿缓存 + 进程内索引 + pub/sub 失效广播(60s TTL 兜底)

**描述**: 用户/令牌/亲和性存 Valkey;渠道索引与定价视图进程内(moka);所有变更发布 pub/sub 失效;TTL 与轮询兜底。
**优点**:
- 变更秒级生效;热路径零 DB
- 降级路径清晰(回源 DB / 内存限流)
**缺点**:
- 失效广播增加实现复杂度

#### 方案 B:纯进程内缓存 + 定时全量同步(原 Go 版模式)

**描述**: 每 60s 全量重建。
**优点**:
- 实现最简单,无 Valkey 依赖
**缺点**:
- 变更生效滞后;多节点窗口期不一致;认证缓存缺失时每请求查库

#### 方案 C:强一致缓存(如 Valkey 事务 + 版本号)

**描述**: 缓存即真相源。
**优点**:
- 一致性最强
**缺点**:
- 复杂度高;与「DB 为准」的运维直觉冲突;故障影响面大

### 决策依据

| 维度 | 权重 | A | B | C |
|---|---|---|---|---|
| 热路径性能 | 高 | ✔ | △ | ✔ |
| 变更时效 | 中 | ✔ | ✘ | ✔ |
| 降级韧性 | 高 | ✔ | ✔ | ✘ |
| 实现复杂度 | 中 | △ | ✔ | ✘ |

## Decision(决策)

### 选择的方案

在 sea-weir 缓存设计中,面对「热路径性能 + 多节点一致 + 降级韧性」的关注点,我们选择 **Valkey 读穿缓存 + 进程内索引 + pub/sub 失效广播(60s TTL 与轮询兜底)**,而非纯进程内或强一致缓存,以获得性能与韧性的平衡,接受失效广播的实现复杂度。

### 决策理由

1. 读穿 + 广播失效同时满足性能与变更时效;TTL/轮询双兜底保证最终一致
2. 以 DB 为真相源,缓存任何时刻可丢弃重建
3. 降级矩阵明确:缓存回源 DB、限流降级内存、会话吊销 fail-close

### 技术架构

| 数据 | 位置 | 键/结构 | TTL | 失效 |
|---|---|---|---|---|
| 用户 | Valkey hash | `user:{id}` | 60s | 写穿透 + pub/sub |
| 令牌 | Valkey hash | `token:{HMAC(key)}` | 60s | 写穿透 + pub/sub;用户禁用批量失效 |
| 渠道索引 | 进程内 moka | group→model→[channel](优先级排序) | 60s 全量同步兜底 | pub/sub 即时失效;状态变更即时摘除 |
| 亲和性 | 进程内 LRU + Valkey | `new-api:channel_affinity:v1:*`(兼容前缀) | 规则 TTL(默认 3600s) | 到期/规则变更 |
| 定价视图 | 进程内 | abilities×models×vendors×倍率合成 | 60s 双检锁 | 倍率/定价变更即时失效 |
| 会话吊销 | Valkey | `sess:revoke:{jti}` | 会话剩余有效期 | 到期自动 |
| 限流窗口 | Valkey(滑动窗口)/ 内存降级 | `rateLimit:{维度}:{key}` | 窗口期 | 到期 |
| 邮件验证码 | Valkey | `verify:{email}` | 10 分钟 | 一次性消费 |

限流维度(与 new-api 对齐):GlobalWeb/GlobalAPI/Critical(IP)、Search/Download/Upload(IP 或用户)、ModelRequestRateLimit(用户,总次数令牌桶 + 成功次数滑动窗口,分组可覆盖配置)。

### 实施计划

1. 实现 cache 抽象(读穿 + 回填)与 pub/sub 失效广播
2. 渠道索引缓存与失效联调;限流中间件双后端(Valkey/内存)
3. 故障演练:Valkey 断连下验证降级矩阵

## Consequences(后果)

### 正面影响

1. 认证/选路热路径亚毫秒
2. 配置与渠道变更秒级全节点生效(原 60s)
3. 降级矩阵文档化,故障行为可预期

### 负面影响

1. 引入 pub/sub 依赖,调试复杂度上升
2. 缓存与 DB 存在最长 TTL 窗口的偏差(余额展示)

### 缓解措施

1. 失效消息带版本戳,乱序丢弃旧消息;保留 60s 轮询兜底
2. 额度类读操作关键路径(预扣)直查 DB,缓存仅服务认证展示

### 长期影响

缓存抽象层为未来接入公司统一缓存平台留口;限流维度可扩展(如按模型)。

## Notes

- 令牌明文不落 Valkey(HMAC 键),与 new-api 安全语义一致
- 定价缓存失效必须广播(计费一致性)
