## Context(上下文)

### 问题陈述

sea-weir 是对 new-api 的重构,**首要设计目标是契约兼容**(§1.2 目标 1)。这意味着测试的
主要职责不是"验证我们想要的行为",而是"验证我们复刻了既有行为"——判定基准在别人的代码里。
同时账务链路(ADR-005)的正确性风险极高:一次计价偏差会持续产生真金白银的账目错误,
且往往在很久之后才被发现。

需要确定:测试怎么分层、判定基准从哪来、什么必须红、CI 卡在哪一层。

### 约束条件

- 骨架阶段全部实现为 `todo!()`,测试必须先于实现存在并**失败**(TDD 红)
- 判定基准是 new-api 的**实际运行行为**,不是文档描述——文档本身已被审查发现多处偏差
- 中继面依赖 35 个外部上游,测试不能真打上游
- 账务测试需要真实数据库的事务与行锁语义,mock 无法覆盖
- 公司 CI 约定:`test/cicd.sh` 按 `ENV` 分发到 `env/<env>.sh`(参照 service-auth)

### 驱动力

- **正确性**:账务与鉴权的缺陷不可接受
- **可执行性**:测试必须能在无外部依赖时跑大部分,否则开发期没人跑
- **防回归**:审查中发现的每一项契约偏差(snake_case、分页基数、取整方式…)都要有测试守住
- **TDD 可操作**:每条用例要给出**具体输入与具体期望值**,而不是"验证行为正确"

### 备选方案

#### 方案 A:四层分层 + 契约基线录制(单元 / 集成 / 契约 / 端到端)

**描述**:
- **单元层**:纯函数与状态机,零外部依赖,`cargo test` 直接跑
- **集成层**:testcontainers 起 openGauss + Valkey,验证事务/行锁/并发
- **契约层**:从 new-api 实例**录制真实请求响应**为 fixture,逐字段比对 sea-weir 输出
- **端到端层**:前端 msw + 后端 live 黑盒冒烟

**优点**:
- 判定基准来自实际行为而非二手文档,能发现文档本身的错
- 单元层可脱离一切依赖跑,开发期反馈快
- 契约层直接对应首要设计目标,是重构项目最该投入的一层

**缺点**:
- 需要一个可运行的 new-api 实例来录制基线(一次性成本)

#### 方案 B:只写单元测试 + 人工联调验收

**优点**:成本最低
**缺点**:契约兼容无自动化保障;字段名/取整/分页这类偏差只能在联调期被人眼发现,而这
正是本项目审查阶段已经证明会漏掉的类别(v1.0 文档带着 4 处 P0/P1 偏差通过了首轮审查)

#### 方案 C:以端到端测试为主(测试金字塔倒置)

**优点**:最接近真实用户路径
**缺点**:账务的并发正确性、35 个适配器的转换细节无法用 E2E 有效覆盖;
运行慢,不适合 TDD 的红-绿-重构循环

### 决策依据

| 维度 | 权重 | A | B | C |
|---|---|---|---|---|
| 契约兼容保障 | 高 | ✔ | ✘ | △ |
| 账务正确性保障 | 高 | ✔ | △ | ✘ |
| TDD 循环速度 | 高 | ✔ | ✔ | ✘ |
| 实施成本 | 中 | △ | ✔ | △ |

## Decision(决策)

### 选择的方案

采用 **方案 A:四层分层 + 契约基线录制**。

### 决策理由

1. **判定基准必须是可执行的 new-api 行为**。本项目审查已经证明,仅凭文档描述会把
   camelCase、0 起分页、错误的计费公式当成"契约"写下去。录制基线让偏差在测试阶段暴露。
2. **账务链路必须有真实数据库的并发测试**。条件原子扣减、`FOR UPDATE` 行锁、
   `request_id` 唯一约束这三条不变量,mock 一条都验证不了。
3. **单元层零依赖**是 TDD 可持续的前提。计价公式、选路加权、重试判定、格式转换都是
   纯函数,这些占了正确性风险的大头却不需要任何外部依赖。

### 测试分层

| 层 | 位置 | 依赖 | 判定基准 | 何时跑 |
|---|---|---|---|---|
| L1 单元 | `code/backend/**/#[cfg(test)]`、`test/src/unit_*.rs` | 无 | 黄金用例表(TEST-VECTORS.md) | 每次提交 |
| L2 集成 | `test/src/integration_*.rs` | openGauss + Valkey(testcontainers) | 不变量断言 | 每次提交(容器可用时) |
| L3 契约 | `test/src/contract_*.rs` | new-api 录制 fixture | new-api 实际响应 | 每次提交 |
| L4 端到端 | `test/src/live_*.rs`、前端 vitest+msw | 已部署实例 | 冒烟断言 | test/prod 环境 |

### 覆盖优先级(TDD 顺序)

按「正确性风险 × 依赖深度」排,详见 `doc/test-design.md` §3:

1. 常量与错误映射(锁死契约取值)
2. 计价公式(黄金用例,4 组已从 new-api 单测提取)
3. 额度扣减与幂等(并发,需真库)
4. 选路与重试/禁用判定(表驱动)
5. 格式转换与流式(回放录制的上游响应)
6. 中继管线编排(mock repo + wiremock 上游,验账目守恒)
7. 路由注册完整性(与 CONTRACTS 附录 A 对表)

### 质量门禁

| 门禁 | 阈值 | 强制环境 |
|---|---|---|
| `cargo fmt --check` | 零差异 | 全部 |
| `cargo clippy -- -D warnings` | 零告警 | 全部 |
| `tsc -b` | 零错误 | 全部 |
| L1 单元测试 | 全绿 | 全部 |
| L2/L3 测试 | 全绿 | test(dev 环境允许因容器不可达跳过并告警) |
| 账务模块行覆盖率 | ≥ 90% | test |
| 其余模块行覆盖率 | ≥ 70% | test |
| 路由数 == CONTRACTS 附录 A(305) | 相等 | 全部 |

**dev 与 test 的差异**:dev 允许"依赖不可达则跳过",test **不允许**——缺连接参数即失败,
杜绝"跳过依赖套件"造成的假绿(沿用 service-auth 的教训)。

## Consequences(后果)

### 正面影响

1. 契约偏差在测试阶段暴露,而非联调或线上
2. 账务的并发缺陷有真实数据库验证兜底
3. 审查发现的每项偏差都有对应测试守住,不会改回去
4. 黄金用例表让 TDD 有具体的红灯目标,而非"感觉应该这样"

### 负面影响

1. 需要维护一个可运行的 new-api 实例用于录制基线
2. testcontainers 使 L2 层在无 Docker 的环境下不可跑
3. 录制的 fixture 会随 new-api 上游演进而过期

### 缓解措施

1. 基线录制脚本化(`test/env/record-baseline.sh`),fixture 入库并标注录制时的 new-api 版本
2. L2 层在容器不可用时降级为跳过 + 告警(仅 dev);CI 的 test 环境提供容器
3. fixture 标注 `recorded_from` 与 `recorded_at`,定期重录;契约测试失败时先确认是
   我方回归还是上游演进

### 长期影响

契约层测试是本次重构的**验收依据**,也是未来灰度切流的信心来源:
只要契约测试全绿,就可以把流量从 new-api 逐步切到 sea-weir。
