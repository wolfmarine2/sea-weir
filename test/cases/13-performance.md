# 13. 性能基线用例

**版本**:v1.0 | **测试代码**:`test/src/perf.rs`
**运行**:`cargo test --release perf -- --ignored --nocapture`

## 定位

**不做门禁**(除非 test 环境显式开启)。目的是发现**数量级退化**,不是卡毫秒。

选 Rust 的理由之一是中继面的长连接性能(ADR-002)。若热路径出现意外开销,
这个理由就不成立了 —— 基线的作用是让退化可见。

## 用例清单

| 编号 | 名称 | 基线 | 关注点 |
|---|---|---|---|
| perf_calculate_quota_throughput | 计价吞吐 | p99 < 10µs | Decimal 比 f64 慢,但不应成为瓶颈 |
| perf_channel_select_with_many_channels | 1000 渠道选路 | 平均 < 50µs | 防止退化成 O(n²) |
| perf_channel_index_rebuild | 索引重建 | < 500ms | 渠道变更时不阻塞请求 |
| perf_sse_chunk_rewrite | 单 chunk 改写 | p99 < 5µs | 决定流式吞吐上限 |

## 说明

### 为什么计价要单独测

`calculate_quota` 在每个请求(以及流式的每次结算)都会执行,且用了 Decimal 全程运算。
Decimal 比浮点慢一个量级是可接受的(正确性优先),但若慢到微秒级以上,
高并发下会成为 CPU 瓶颈。若超标,考虑对"倍率均为整数"的常见情况走快路径。

### 为什么选路要按渠道数测

选路的复杂度应该是 O(候选数),不是 O(总渠道数)。
若实现时每次都遍历全表过滤,渠道多了就会线性退化 —— 而这在开发环境
(几个测试渠道)完全暴露不出来。

### 与压测的区别

本组是**微基准**,只测单个函数。整体吞吐、并发连接数、内存占用属于压测范畴,
在 `security/` 或独立的压测流程中做,不在本目录。
